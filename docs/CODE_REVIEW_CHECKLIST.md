# Code Review — 독립 검수 기준

Reviewer는 요구사항·실제 diff·주변 호출자·테스트를 직접 확인한다. Builder 설명만으로 통과시키지 않는다. [Done](DEFINITION_OF_DONE.md)은 상태 판정, 이 문서는 결함을 찾는 질문과 보고 형식을 소유한다.

## 역할과 절차
1. Builder는 구현과 자체 검증 증거를 제공한다.
2. Reviewer는 별도 관점으로 아래 질문을 확인한다. 가능한 경우 별도 세션/담당자를 사용하고 실제 독립성 수준을 기록한다.
3. Fixer는 지적 근거를 확인해 수정하고 영향받는 검증을 다시 실행한다.
4. Reviewer는 수정 결과와 새 회귀 위험을 확인한다. 독립 Reviewer는 별도 AI 또는 사람일 수 있다. 팀원의 GitHub Approve는 선택 사항이며, PO의 명시적 병합 승인과 최신 CI 통과는 별도로 필요하다.

별도 검토가 없으면 “자체 점검”으로 기록한다. 팀원 이름이나 승인 결과를 만들어내지 않는다.

## 요구사항과 범위
- [ ] AC를 만족하는 실제 사용자 행동이 있는가? 놓친 실패·경계 조건은 없는가?
- [ ] 정책 변경이 승인된 범위인가? 관련 없는 리팩터링·의존성 변경이 섞이지 않았는가?
- [ ] 선행 기능/공유 계약의 가정이 다른 팀원의 작업과 맞는가?

## 설계와 이해 가능성
- [ ] 기존 패턴·공통 UI·용어를 활용했는가?
- [ ] 정책·상태를 중복 구현하지 않았는가? 불변조건을 깨뜨릴 경로는 없는가?
- [ ] 새 추상화·의존성·최적화의 가치가 복잡성보다 큰가?
- [ ] API 입력·출력·오류·권한·부작용과 구버전 호환성이 명확한가?
- [ ] 죽은 코드·미사용 의존성·임시 flag가 남거나 필요한 코드가 잘못 삭제되지 않았는가?

## 보안과 데이터
- [ ] 타인 자원·관리자 기능·파일 접근의 서버 권한 검사에 우회 경로가 없는가?
- [ ] 클라이언트가 핵심 값을 조작할 수 없는가? 입력·남용·개인정보·비밀 노출을 확인했는가?
- [ ] 중복·재시도·동시 요청에서 원자성·유일성·상태 전이가 유지되는가?
- [ ] 네트워크/저장소/DB 부분 실패 뒤 데이터가 일관된가?
- [ ] migration이 기존 데이터·실행 시간·호환성·충돌·실패 재실행·복구를 다루는가?

## 검증과 운영
- [ ] 테스트가 구현 복사나 happy path에 그치지 않고 중요한 위험을 검증하는가?
- [ ] 수정된 버그와 주변 기능의 회귀를 검증했는가?
- [ ] UI의 오류/빈 상태/로딩·모바일·관련 접근성을 확인했는가?
- [ ] 필수 CI가 최신 변경에서 실행되었는가? skip이나 약화로 실패를 숨기지 않았는가?
- [ ] 실패를 발견·진단할 신호와 복구 절차가 실행 가능한가?
- [ ] 코드·정책 문서·결정 기록·실제 배포 계획이 일치하는가?

## 결과 작성
- 검토자 / 역할 / 대상 커밋 / 범위:
- 수행한 확인과 실행하지 못한 확인:
- 지적사항별: 심각도, 파일/위치, 발생 조건, 사용자/데이터 영향, 근거, 최소 수정 제안.
- 판정: 변경 요청 / 승인 / 검토 미완료.
- 수정 후 재확인 결과:

**차단:** 요구사항 오류, 권한 우회, 데이터 손실·중복 지급, 핵심 불변조건 위반, 필수 검증 실패/누락 등은 병합 전에 해결한다.
**비차단 제안:** 동작 안전성에 영향 없는 스타일·후속 개선은 차단 항목과 구분하고 필요하면 담당자 있는 Issue로 남긴다.

“문제 없음”은 검토 범위에서 발견하지 못했다는 뜻이다. 미검증 영역까지 안전을 보장한다고 쓰지 않는다.
