# Mission / Proof / Score 구현 설계 제안

- 상태: Accepted (구현 범위 승인). 작성일/승인일 2026-09-21.
- 대상: 실제 상세/보드/카메라, 비공개 사진 제출, 서버 자동 인정과 점수 반영.
- 기존 승인: Google 로그인, Camera 전용, 기술 검증 후 자동 인정, 100/70/40점, Day31 종료 후72시간 마감, 마감30일 후 사진 삭제. 변경하지 않는다.
- 적용 권한: 핵심 DB/권한/개인정보 설계는 Level 3. 이 문서는 승인 사실을 만들지 않는다.

## 추천안

1. 기존 migration은 수정하지 않고 추가 migration으로 missions에 steps/submission_items/completion_criteria_items 배열 및 proof_guide, content_version을 추가한다. 기존 purpose/guide/completion_criteria는 호환 보존. 31일 카탈로그는 단일 원본으로 관리하고 검증된 개발 seed를 생성한다. 실제 챌린지 데이터 덮어쓰기/운영 적용은 하지 않는다.
2. 사용자·참가·미션·이미지경로·상태·처리시각·정책버전을 가진 Proof/제출시도 기록을 추가한다. 동일 참가자/미션의 유효 인정은 하나만 허용한다. 요청 키와 이미지 hash로 같은 요청 재시도는 기존 결과, 같은 키/다른 내용은 충돌 처리한다.
3. 브라우저는 사진을 앱 서버로 전송한다. 서버가 검증한 사용자/참가/해금/마감과 실제 이미지 디코딩을 확인한 뒤 Private Storage에 저장한다. 클라이언트에 Storage 직접 쓰기나 Score INSERT 권한을 주지 않는다. 서버 전용 secret은 환경변수로만 관리하며 로그/브라우저에 노출하지 않는다. 서비스 권한은 RLS를 우회하므로 서버 소유권 검증 및 서버 전용 DB 함수 제한이 필수다.
4. 이미지 제한 제안: JPEG 입력 최대 4 MiB/20메가픽셀, 서버에서 디코딩 후 긴 변 최대1600px JPEG로 재인코딩하여 위치 등 EXIF 제거. 기존 Next에서 사용하는 sharp를 직접 의존성으로 명시해 사용한다(버전은 lockfile 확인 후 고정). UI는 카메라만 제공하고 파일 선택은 제공하지 않는다. 웹 요청만으로 실제 카메라 출처나 촬영 내용의 진위를 증명할 수는 없다.
5. DB에서 요청 예약/사용자별 동시 제출 제한을 처리하고, 서버 검증 시각을 저장해 점수 경계를 고정한다. 저장 성공 후 인정/Score Event를 한 DB 트랜잭션으로 처리한다. 마감 이전 예약만으로 무기한 제출하지 않도록 시도 만료를 둔다. 인정된 Proof 재제출은 추가 점수 없이 기존 결과로 돌려준다.
6. Storage와 DB는 하나의 트랜잭션이 아니므로 실패시 정리 상태를 기록한다. 응답 유실 시 객체를 즉시 삭제하지 않고 먼저 DB 최종 상태를 조회한다. 불확실하면 재처리 대상으로 남긴다. 미완료 객체 정리/보존기간 종료 삭제는 재실행 가능한 서버 관리 명령과 기록으로 구현한다. 배포 스케줄 등록은 배포 작업에서 수행한다.
7. 실제 UUID 상세/보드/카메라/결과 라우트와 API는 동일 서버 조회를 사용한다. 서버 확정 상태/점수/마감만 표시한다. 잠긴 미션 상세는 노출하지 않고 보드에는 일차/잠금 메타데이터만 표시한다. 기존 프리뷰와 실제 데이터 경계를 유지한다.

## 대안과 비용

- 브라우저 직접 Storage 업로드는 서버 전송 부담이 적지만 검증 전 업로드 권한, 중복/남은 객체 정리 경계가 복잡하다. 이번에는 서버 경유를 추천한다.
- 카탈로그를 코드에만 두면 migration이 적지만 DB 콘텐츠와 버전의 중복 기준이 생긴다. 명시적 추가 필드와 단일 원본 seed를 추천한다.
- 이미지 크기 제한/축소는 원본 세부 해상도를 일부 포기하지만 모바일 전송과 메모리·저장 비용을 줄인다. 촬영 미리보기에서 작은 글씨 가독성을 실제 기기로 확인해야 한다.

## 검증 및 범위

- 단위: KST 자정/마감/유효하지 않은 입력, 이미지 크기/형식/디코딩 실패.
- DB: 타인 접근/미참가/잠금/마감/중복 키/동시 인정/점수 원자성/재시도.
- 서비스: Storage 실패/DB 실패/응답 유실/정리 재시도. 가짜 저장소 테스트와 실제 Supabase 검증을 구분한다.
- E2E: 실제 라우트 기반 홈/보드→상세→촬영→제출→결과/총점. 오류 후 재시도 포함.
- check/build/CI 및 사람 리뷰 필요. 외부 서비스 설정/실제 기기/운영 적용이 없으면 코드·로컬 검증 완료까지만 주장한다.
- 제외: Vercel 연결/배포, 운영 DB migration, 유료 결제, 새로운 OAuth 공급자, AI 판정, 금전 지급.
- 승인 필요: 위 추가 schema, 서버 전용 저장 권한, 이미지 제한·재인코딩과 sharp 직접 의존성, 저장/정리/시간 경계 설계. 기존 제품 정책의 재승인을 요구하는 것은 아니다.
