# 프로젝트 전체 PR 병합 기준

- 상태: Accepted — PO가 프로젝트 전체 적용을 명시적으로 요청한 결정의 기록.
- 결정자/결정일: PO(현재 작업 사용자, GitHub `ths4114-cloud`) / 2026-09-21.
- 근거: 현재 Codex 작업 `01a0b3ca-25a2-7472-9115-3e1b929e8953`에서 PO가 “PR #2뿐 아니라, 전체 프로젝트에 대해서 적용해달라고 부탁했던거야!”라고 적용 범위를 명확히 했고, 이어 “MVP 작업 범위 중 merge가 안된 부분은 마저 merge해줘”라고 실행을 요청했다. 이 결정과 해당 승인 근거를 규칙 변경 PR 및 대상 기능 PR에 연결한다. GitHub Approve 이벤트를 대신 만들어내지 않는다.

## 배경과 대안

기존 문서에는 팀원 한 명 이상의 사람 리뷰가 필수였고, 2026-09-18 기록은 PR #2에만 예외를 허용했다. PO가 요청한 것은 프로젝트 전체의 팀원 Approve 필수 요건 해제였으므로 공통 지침·개발 흐름·Done·체크리스트·PR 템플릿을 일치시킨다.

- 대안1: 기존 팀원 Approve 필수 유지 — 추가 사람 검토를 보장하지만 팀원의 응답 대기로 병합이 멈출 수 있다.
- 선택한 대안2: 팀원 Approve 선택, 독립 리뷰·CI·충돌 해결·PO 병합 승인 필수 — 승인 대기를 줄이되 기술 검증과 병합 책임은 유지한다.
- 배제한 대안3: 리뷰/CI 없는 자동 병합 — 결함·정책 오류를 발견할 보호 장치가 없어 채택하지 않는다.

## 적용 기준

1. 프로젝트의 모든 PR에 적용한다. 특정 PR 번호, MVP 기간에만 한정하지 않는다. 이 규칙을 반영하는 PR에도 적용한다.
2. 팀원의 GitHub `Approve`는 선택 사항이다. 없는 승인을 있다고 표시하지 않는다.
3. 작성자와 분리된 AI 또는 사람 Reviewer가 검토하고, 미해결 차단 지적이 없어야 한다. 작성자의 자체 점검만으로 대신하지 않는다. 변경 후 필요한 재검토를 수행한다.
4. 최신 변경의 필수 CI가 모두 성공하고 main/선행 PR과의 충돌·의존성이 해결돼야 한다. 실패·미실행·대기 중 검사를 성공으로 취급하지 않는다.
5. PO가 해당 PR 또는 명확하게 지정한 작업 범위의 병합을 승인해야 한다. 이 규칙 자체는 향후 모든 PR에 대한 포괄적 병합 승인이 아니다. 승인 범위를 넘어서는 변경은 다시 확인한다.
6. 직접 main push 금지, 별도 브랜치/PR 사용, 기존 데이터 보호, Level 3 변경 사전 승인 원칙은 그대로 유지한다.
7. 병합은 배포·운영 DB 적용·비밀 키 등록·유료 비용 발생의 승인이 아니다.
8. GitHub 서버 보호 설정은 문서와 별개다. 필요한 보호 설정이 병합을 막으면 관리자 강제 우회하지 않고 해당 설정 변경을 별도 확인한다. 이 작업에서 필수 CI나 보호 규칙을 임의 제거하지 않는다.

## 영향·책임·재검토

- 포기하는 보호 장치: 모든 PR에 대한 별도 팀원의 의무 검토. 보완책: 독립 리뷰 증거, 최신 CI, PO 승인 기록을 각 PR에 남긴다.
- 책임: PO가 병합 범위와 위험 수용을 결정하고, 구현 담당 AI/개발자가 검증·미검증·리뷰 결과를 정확히 기록한다.
- 유효 범위: 프로젝트 전체, 후속 결정으로 대체될 때까지. 인증·DB 등 고위험 영역의 전문 검토나 Level 3 승인은 생략하지 않는다.
- 재검토 조건: 리뷰 누락·반복 회귀·운영 사고가 발생하거나 팀 협업 방식이 변경되면 기준을 재검토한다.
- 과거 [PR #2 한정 예외](2026-09-18-foundation-merge-gate-exception.md)는 당시 기록으로 보존한다. 현재 병합 기준은 본 결정이며 과거 승인 사실을 소급 변경하지 않는다.
